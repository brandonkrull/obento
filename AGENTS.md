# AGENTS.md

Notes for coding agents working on obento. Read README.md for what the project is and docs/RUNBOOK.md for
procedures; this file covers how to change it safely.

## What this is

Bash, Docker Compose and config files that turn one Ubuntu Server 24.04 machine into a family home server
(Immich, Vaultwarden, OpenCloud, Jellyfin, AdGuard Home, Scrutiny, a portal), with ZFS, alerts, snapshots and
backups. The author's server is named `tamago`; the command that manages the apps is `obento`. Don't confuse
the two: `tamago` in docs is a hostname (`ssh tamago`, `tamago.<tailnet>.ts.net`), `obento up` is the CLI.

Real family data lives on this server. Prefer small, verifiable changes over clever ones.

## How changes reach the server

1. Edit the repo on the workstation (`~/devel/obento` on the author's Mac), commit, push to GitHub.
2. On the server: `obento update` (= `git pull` in `~/obento` + `sudo ./install.sh`).
3. `obento up` when the compose file or `.env` changed.

Never edit files on the server: `install.sh` overwrites the installed copies. The server pulls with a
read-only deploy key and can't push.

| On the server | What it is |
|---|---|
| `~/obento` | the clone; source of truth on the server, including `.env` (mode 600, never committed) |
| `/opt/obento` | root-owned copy that systemd timers and compose run from; overwritten by `install.sh` |
| `/etc/obento/.env` | live settings and secrets, root only; `compose/.env` links here |
| `/opt/obento/compose/docker-compose.override.yml` | generated by `install.sh` (OpenCloud URL, Vaultwarden DOMAIN); don't edit |
| `/opt/obento/compose/files`, `/opt/obento/modules.on`, `/opt/obento/generated/` | generated by `install.sh`: compose files, modules on, Traefik routes |
| `/srv/...` | app data on the SSD; moves to `/tank/...` after the pool exists (RUNBOOK step 6) |

Always manage apps with `obento` (`obento help`), never `docker compose` from the repo: it wouldn't see the
live settings.

## Working on the server as an agent

- `ssh tamago` works over Tailscale SSH as the owner's user. It may print a `login.tailscale.com` check link.
- There is no passwordless sudo. Anything needing root (`install.sh`, `docker`, `obento` itself, reading
  `/etc/obento` or container logs) must be handed to the user as exact commands to run. Ask them to paste
  output back.
- You can read without sudo: the repo, `journalctl -t obento` (alerts), `systemctl list-timers 'obento-*'`,
  `tailscale serve status`, `ss -ltn`, `/srv/opencloud` (owned by UID 1000), `curl` against localhost ports.
- Check what users will see from the workstation too: `curl --resolve name:443:<tailscale ip> https://name/`
  isolates DNS problems from app problems.

## Secrets

Never print, commit or paste into chat: anything from `.env` (`NTFY_TOPIC`, `NTFY_TOKEN`, `NTFY_EMAIL`,
`DESEC_TOKEN`, `USENET_PASSWORD`, `NZB_INDEXER_API_KEY`, `OPENSUBTITLES_PASSWORD`, B2 keys, `RESTIC_PASSWORD`, app passwords), OpenCloud's generated secrets in
`/srv/opencloud/config`, or private keys. Redact when showing config (`sed` the value out). `.env.example`
holds placeholders only. The ntfy topic is effectively a password: anyone who knows it can read alerts.

## install.sh rules

- Idempotent and safe to re-run; it never touches the hard drives.
- Copy config with `install_conf` (copies only when content differs) and restart services with
  `restart_if_stale` (only when their config changed). smartd sends a test alert per drive on every restart,
  so unconditional restarts spam the family's phones.
- `obento-apps-stop.service` runs `obento stop` at shutdown, because Docker's `live-restore` leaves the apps
  running for systemd to kill. Never restart or stop it on a running server: that stops every app.
- `apt-get` is wrapped to wait for unattended upgrades instead of failing on the dpkg lock.
- Kernel packages are held on purpose (the HWE kernel is needed for the RTL8125 NIC; kernel updates are manual,
  RUNBOOK "Kernel updates"). Don't unhold them.
- Optional parts are **modules** (`modules/<name>/`, see `modules/README.md`), switched on by `MODULES` in
  `.env`; put a new optional app or feature in a module rather than adding `if`s to `install.sh`. Without
  `MODULES`, `scripts/modules.sh` derives the pre-module setup (`opencloud ups` plus the old `COMPOSE_PROFILES`).
  Smaller options stay `.env` settings (`OPENCLOUD_APP_TOKENS`, `NTFY_EMAIL`, ...). With a setting unset,
  behaviour must stay exactly as before.
- `obento` runs compose with the file list `install.sh` writes to `/opt/obento/compose/files` (core, each
  module's `compose.yml`, the override); `obento up` without app names removes the apps of modules turned off.

## Destructive scripts

`scripts/burnin.sh` erases the drive it's given. `scripts/create-pool.sh` builds the ZFS pool. Never run
them, and never suggest running them without the user confirming the exact `/dev/disk/by-id/...` paths.

## Addresses and ports

Without `APPS_DOMAIN`, `install.sh` publishes apps through `tailscale serve`
(`tamago.<tailnet>.ts.net` on 443/8443/8920/9200). With it (the author's setup), Traefik answers
`photos.` / `passwords.` / `files.` / `media.` / `adblock.` / `drives.` `<APPS_DOMAIN>` and the portal at
`<APPS_DOMAIN>`, and Tailscale serves nothing. With the `downloads` module too: `requests.` (Seerr), `tv.`
(Sonarr), `movies.` (Radarr), `downloads.` (SABnzbd), `indexers.` (Prowlarr), `subtitles.` (Bazarr).

| Port (host) | What |
|---|---|
| 53 | AdGuard DNS for the home network |
| 80, 443 | Traefik (domain setup only) |
| 2283 | Immich |
| 3000 | AdGuard admin |
| 3010 | portal (127.0.0.1 only) |
| 3011 | UPS battery for the portal, `modules/ups/ups-status.py` (127.0.0.1 only) |
| 3012 | Hard drive (pool) space for the portal, `scripts/pool-status.py` (127.0.0.1 only) |
| 5055 | Seerr (127.0.0.1 only) |
| 6767 | Bazarr (127.0.0.1 only) |
| 7878 | Radarr (127.0.0.1 only) |
| 8080 | Scrutiny |
| 8085 | SABnzbd (127.0.0.1 only; 8080 inside its container) |
| 8096 | Jellyfin |
| 8222 | Vaultwarden |
| 8989 | Sonarr (127.0.0.1 only) |
| 9201 | OpenCloud (127.0.0.1 only) |
| 9696 | Prowlarr (127.0.0.1 only) |

Pick a free port (`ss -ltn` on the server) before adding a service. Things that bit us:

- **Routing** is written by `install.sh` (`scripts/modules.sh`) from `HOSTS` in each module's `module.conf`
  into `/opt/obento/generated/routes/`; routers match the first label (`HostRegexp(^photos\.)`), so no domain
  is hard-coded, and `HOST_<NAME>` in `.env` renames one. Traefik, OpenCloud and the portal use host networking and reach apps on
  `127.0.0.1`.
- **Certificates**: one Let's Encrypt certificate for `<APPS_DOMAIN>` + `*.<APPS_DOMAIN>`, proved by DNS-01 at
  deSEC, which hosts `APPS_DOMAIN` (delegated with NS records from the domain's own DNS). Keep the 120 s
  propagation delay: without it Let's Encrypt's secondary validation finds no TXT record. Failed validations
  are rate-limited (5 per hour per name).
- **OpenCloud** accepts sign-ins at exactly one URL (`OC_URL`, written into the override). When it changes,
  `install.sh` deletes `idp/tmp/identifier-registration.yaml` so OpenCloud regenerates its sign-in client
  list; every user signs in again once.
- **Changing an address** means every family device must be updated (Immich, Bitwarden, OpenCloud, Jellyfin
  apps). Plan it with the user; don't change addresses casually.

## Alerts

`obento-notify <low|default|high|urgent> <title> <message>` sends to ntfy (high and urgent also by email when
configured) and logs under `journalctl -t obento`. Alerts land on the family's phones: don't send test alerts
without asking.

## Verify before you push

- `bash -n` and `shellcheck` on every changed script (only SC1091 "not following" infos are expected).
- Compose: `docker compose --env-file /dev/null config` in `compose/` with the needed variables set inline
  with `-f` for each module's `compose.yml` (`compose_files` in `scripts/modules.sh` lists them) and the needed
  variables set inline (for example `APPS_DOMAIN=home.example.com SSD_DATA=/srv ...`); try with and without the
  modules.
- YAML: parse it (`ruby -ryaml -e 'YAML.load_file(ARGV[0])' file`).
- Logic that runs as root: extract it and run it against temporary paths or with the root-only step replaced
  by `echo`, on the server if it depends on the server's state.
- After the user applies a change, check the result yourself (timers, `curl` the addresses, certificates,
  `journalctl -t obento` for failed alerts) and say what you verified and what you couldn't.

## Docs

Update docs in the same commit as the behaviour they describe:

- `README.md`: the front door for anyone using the repo; generic placeholders (`home.example.com`,
  `<tailnet>`), the author's build only as an example.
- `docs/RUNBOOK.md`: the authoritative step-by-step for the server; numbered steps are referenced elsewhere,
  so check links when renumbering.
- `docs/MAC-SETUP.md`, `docs/IOS-SETUP.md`: for family members; plain language, no server internals.
- `docs/DRIVE-PLAN.md`: why the storage works the way it does.

Write plainly: say what something is for before naming the tool, explain why a step matters, keep commands
copy-pasteable. Commit messages: a short imperative summary, then what changed and why.

## Memory

`MEMORY.md` at the repo root is the running record of this server: its current state, open items, decisions
and changes. It's git-ignored, because it describes one person's server and the repo may be published: it
stays in the local clone and is never committed. Read it before starting work if it exists (create it with
the sections below if it doesn't); it says what's true now, which the code alone can't (what's applied, what's
pending, what the owner decided to defer).

Update it alongside every change:

- **Current state**: rewrite in place so it stays true. Update the date at the top.
- **Open items**: add what's left to do or waiting on the owner; remove items once done.
- **Decisions**: append `- YYYY-MM-DD: <decision>. Why: <reason>.` for anything a later agent might otherwise
  undo or relitigate (a choice between options, something deliberately not done).
- **Change log**: newest first, under a `### YYYY-MM-DD` heading. One line per change: what changed, the
  commit(s), and whether it was applied on the server and how it was verified (or that it wasn't).

Because it isn't committed, personal details are fine there (domain, hostnames, what the family uses), but
still no secrets.

Use absolute dates, keep entries to a line or two, and never record secrets (tokens, passwords, the ntfy
topic, email addresses).
